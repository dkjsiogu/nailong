# 20 · 测一下这台电脑，内存从游戏里学

> 公式（[19](19-jvm-tuning.md)）按 Mod 数量和经验估算。0.36 起，调参的两个问题分开回答：
>
> - **用哪个回收器**取决于电脑和 Java，和装了什么 Mod 关系不大。由一个通用测试回答：不开游戏，用一个内置的小 Java 程序模拟游戏负载，结果所有版本共用。代码在 `crates/nailong-core/src/bench.rs`，负载程序在 `crates/nailong-core/assets/jvmbench/`。
> - **给多少内存**取决于这套 Mod、这个世界、这个视距。由真实游戏回答：每局都记下回收日志，退出后读出存活数据，下次按它算。代码在 `crates/nailong-core/src/learned.rs`。
>
> 0.35 的做法（给每个版本复制一份测试实例、进测试世界飞行）已经删掉：慢（5–10 分钟）、要开游戏窗口、每个版本都要测一次，还要维护世界模板和数据包。

## 1. 体验

**测一下这台电脑：** 设置 → 性能卡片 → 「测一下」。确认弹窗写清楚会发生什么：

- 不开游戏，也不碰任何版本：后台跑一个模拟游戏负载的小程序。
- 比平均帧率、1% 低帧、能看出来的顿和 CPU，分常规和大型整合包两档。
- 每个 Java 约 1 分半，期间电脑会比较忙，可以随时停止。
- 内存大小不在这里测：正常玩一局，启动器会从游戏里学。

跑完回到设置，卡片里写「今天测过这台电脑：Java 21 常规档 G1、大型整合包档 ZGC」，展开「查看计算」能看到每一轮的数字。电脑的线程数或内存变了，卡片提示结论不再使用。

**内存：** 不用做任何事。没玩过的版本卡片里写「内存现在按公式估算；正常玩一局后改按游戏里的实测」，玩过之后依据变成「按最近 3 局游戏实测：存活数据最多 2.1 GB」。

命令行：`nailong bench`，打印每个 Java、每一档的数字和结论。

## 2. 通用测试

### 2.1 负载程序

`NailongBench.java` 编译成 Java 8 字节码（`javac --release 8`），一个 7 KB 的 class 文件嵌在启动器里，所以 Java 8 到 25 都能跑，构建启动器也不需要 JDK。运行时写到 `cache/nailong/jvmbench/`，`java -cp . NailongBench …`，不开窗口。

它照 Minecraft 客户端的特征造负载：

| 部分 | 模拟什么 | 对回收器的意义 |
|---|---|---|
| 常驻数据 | 注册表、方块状态（互相引用的小对象）和模型、纹理（4 KB 数组） | 每次标记都要走一遍 |
| 区块缓存 | 每个区块约 80 KB（24 个分段、光照、方块实体），生成线程不断替换 | 活得够久被晋升，再在老年代里死去：老年代回收靠它检验 |
| 生成线程 | 按固定速率生成区块，同时产生噪声计算的临时数组 | 中等寿命对象 + 大量垃圾 |
| 服务端 | 每 50 ms 一个 tick：移动实体、随机读世界、产生临时对象 | tick 耗时 |
| 渲染 | 不封顶帧率，每帧读 512 个区块拼顶点缓冲 | 停顿直接拉长这一帧；并发回收抢走的 CPU 和读屏障拉低平均帧率 |

速率都是固定的，所以同一台电脑上换回收器，帧率、tick 耗时和生成速度的差别就是回收器的影响。帧率是模拟负载的帧率，只用来横向比较，不是游戏帧率。

### 2.2 两档

| 档位 | 常驻 + 缓存 | 区块/秒 | tick 垃圾 | G1 堆 | ZGC 堆 |
|---|---:|---:|---:|---:|---:|
| 常规（原版、轻量 Mod） | 0.7 + 0.3 GB | 120 | 15 MB | 2 GB | 2.5 GB |
| 大型整合包 | 2.2 + 0.8 GB | 200 | 25 MB | 5 GB | 6.5 GB |

堆按和正式启动相同的规则算（G1：存活 ÷ 0.6 且至少多 1 GB；ZGC：存活 ÷ 0.5 且不少于 G1 的 1.25 倍），回收器参数直接用 `tuning::plan` 生成，和启动游戏时一模一样，再加两项：

- `-XX:+AlwaysPreTouch`：只测十几秒，第一次碰到新内存的缺页会盖过回收器本身的差别。实测不加时大档 ZGC 最长一帧 130 ms，加了之后 31 ms。
- `-Xlog:gc,gc+phases:file=gc.log:uptime:filecount=0`：停顿统计。

电脑放不下大档 ZGC 的堆，或者测试那一刻空闲内存不够（会被换到交换区，数字不准），就跳过大档。

### 2.3 测哪些 Java

64 位、21 起（分代 ZGC）、不是 GraalVM（它用 ZGC 时会关掉自己的编译器），每个大版本只测启动游戏时会选中的那一个。Java 8/11/17 只能用 G1，没什么可选的。每轮预热 3–4 秒、测量 12 秒，一个 Java 两档四轮约 70 秒。

### 2.4 怎么判断

每轮记：平均帧率、1% 低帧（最慢 1% 的帧换算成帧率）、每分钟能看出来的顿（比中位帧多出 8 ms 以上而且慢了一半）、tick P95、区块生成速度、进程 CPU。每一档给两个结论：

- **一般版本**：G1 已经不顿就留 G1。只有 G1 每分钟顿 10 次以上（一轮里两次以上；一次算噪声）或者最长一帧比平均多 25 ms，而且 ZGC 更顺（顿的次数减半且 1% 低帧不低，或 1% 低帧高 10%）、平均帧率和生成速度不低于 G1 的 97%、多用的 CPU 不超过总线程的 10%，才换 ZGC。
- **官方默认 ZGC 的版本**（26.1 起）：Mojang 在大量机器上验证过，沿用 ZGC，除非它在这台电脑上明显更差：1% 低帧低 15% 以上、每分钟多顿 8 次以上、平均帧率或生成速度低于 95%，或多用的 CPU 超过 20%。

### 2.5 结果怎么用

存进 `<数据目录>/jvm-bench.json`，记下测试时的线程数和内存（整 GB），变了就不再使用。启动时按选中的 Java 找结论（先找同一个程序，再找同一个大版本），按这个版本有多大挑档位：

- 玩过：实测存活 2 GB 以上看大型整合包档。
- 没玩过：公式需要量 6 GB 以上（约 130 个 Forge Mod）看大型整合包档。公式本身偏宽松，所以门槛比存活高。

回收器设成「自动」时用这个结论，优先于官方默认和经验公式；手动选择照样优先。

## 3. 从真实游戏里学内存

每次启动都加 `-Xlog:gc:file=logs/nailong-gc.log:uptime:filecount=0`（Java 9 起、HotSpot；Java 8 和 OpenJ9 只按公式）。路径相对游戏目录：游戏以游戏目录为工作目录启动，相对路径里没有 Windows 盘符的冒号，不会和 `-Xlog` 的分隔符冲突；`logs/` 在启动前建好，否则 JVM 打不开文件会拒绝启动。`filecount=0` 让每局覆盖写、不轮转，一局只有几百 KB。

游戏退出后：

- **存活数据** = 清理过老年代的回收（G1 混合/整堆、ZGC 大回收）之后剩下的最大值。启动后 3 分钟内的不算：那时在加载 Mod 和资源，元数据触发的混合回收会量出偏小的数（实测 NeoForge 停在主菜单时只有 0.2 GB）。一局里没有这类回收就不知道，不猜。
- **压力**：出现整堆回收或晋升失败，说明堆偏小，记下这一局的堆。

按「版本 + 游戏目录」存进 `<数据目录>/learned.json`，每个版本留最近 5 局，带 Mod 列表的指纹，换了 Mod 就清空重学。内存为「自动」时：

- 有存活数据：取最近几局里最大的，G1 给 存活 ÷ 0.6（至少多 1 GB），ZGC 给 存活 ÷ 0.5（不少于 G1 的 1.25 倍）。
- 最近几局出过压力：至少给那一局的堆加 1/4。
- 都没有：按公式。

## 4. 验证

单元测试覆盖结果行解析、嵌入的字节码版本（52）、Java 挑选、回收器决策（含一次顿算噪声、本机两次实测的数字）、按路径和大版本找结论、两档的挑选、GC 日志解析（G1、ZGC、JDK 11 单独一行的 To-space exhausted、默认装饰）、从游戏日志读一局、加载阶段不算、按版本记录和换 Mod 后清空、存活和压力对堆的影响。

实机（Linux、i5-13490F 16 线程、16 GB、Ubuntu OpenJDK 21 和 25），`nailong bench` 一次约 2 分 15 秒。第二次的数字：

| Java | 档位 | G1：平均 / 1% 低 / 顿每分 / tick P95 | ZGC：平均 / 1% 低 / 顿每分 / tick P95 | 一般版本 | 官方 ZGC 版本 |
|---|---|---|---|---|---|
| 21 | 常规 | 264 / 237 / 0 / 3.6 ms | 275 / 240 / 0 / 3.5 ms | G1 | ZGC |
| 21 | 大型整合包 | 256 / 222 / 25 / 3.8 ms | 270 / 226 / 0 / 5.0 ms | ZGC | ZGC |
| 25 | 常规 | 331 / 287 / 5 / 2.5 ms | 355 / 289 / 0 / 3.7 ms | G1 | ZGC |
| 25 | 大型整合包 | 327 / 257 / 20 / 3.8 ms | 354 / 274 / 0 / 5.2 ms | ZGC | ZGC |

两次测得的趋势一致：常规档两边都很顺，大档 G1 每分钟顿 15–25 次而 ZGC 不顿、平均帧率还高 5%–8%。第二次也暴露了一处规则问题：一开始拿 tick P95 和 G1 比相对值，3.8 → 5.0 ms 就被判成拖慢，大档因此留在 G1；tick 的预算是 50 ms，现在 P95 在 25 ms 以内都算跟得上。读结果时按当前规则从测到的数字重新判，所以这类修正不需要重测。

真实启动 NeoForge 1.21.1（Xvfb + llvmpipe）：带 GC 日志参数正常进主菜单，`logs/nailong-gc.log` 正常写出，退出后记下一局。Java 11、17、21、25 和 GraalVM 21 都确认 `filecount=0` 覆盖写、不轮转，生成的参数在每个 Java 上都能启动。

**局限：** 负载是模拟的，反映的是这台电脑和 JVM 的特性，不能用来比较具体的 Mod；Windows 实机还没跑过；学内存至少要玩一局三分钟以上、而且发生过老年代回收才有数据。
