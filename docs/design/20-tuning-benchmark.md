# 20 · 实测调优

> 公式（[19](19-jvm-tuning.md)）只能按 Mod 数量估算。实测调优在用户自己的电脑上，用这个版本的 Mod 真跑几轮游戏，量出它需要多少内存、G1 和 ZGC 哪个更合适。结果存进数据目录，之后的「自动」直接按实测值启动。代码在 `crates/nailong-core/src/bench.rs`。

## 1. 体验

设置 → 性能卡片 → 「实测调优」，确认弹窗说明会发生什么：

- 会打开游戏窗口，在测试世界里自动飞行，不需要操作。
- 跑 2–3 轮，每轮加载游戏、再飞 1 分钟，一共约 5–10 分钟。
- 用单独的测试实例，不碰存档和设置；声音关掉。

测试期间启动器显示进度页，可以随时停止。跑完回到设置，卡片里显示结论和每一轮的数据。之后 Mod、Java 大版本或电脑内存变了，卡片提示结果过期，启动退回公式。

命令行：`nailong bench <版本>`，打印每轮数据和结论。

## 2. 怎么做到无人值守

Minecraft 客户端需要窗口，不能真正无头运行。我们让它自己跑完，不需要人：

1. **测试实例**：在 `cache/bench/<版本>/` 建一个游戏目录，复制 `mods`、`config`、`resourcepacks`、`shaderpacks` 等决定加载内容的目录。jar 和 zip 用硬链接；其他文件游戏可能原地改写，一律真复制，免得改到用户的文件。存档、日志、地图缓存不复制。`options.txt` 保留用户的画面设置（视距会影响内存），只改掉会挡住测试的项：失焦暂停、首次引导、旁白、全屏、声音。
2. **测试世界**：内置两个只有几 KB 的模板，不含地形，地形由固定种子现场生成。
   - 1.20.1 创建的 `level.dat`：1.20–1.21 打开时静默升级。
   - 26.1 创建的 `level.dat` 和 `data/minecraft/*.dat`：26.x 打开任何更旧的世界都会弹「升级前备份」提示，所以按目标版本 `version.json` 里的 `world_version` 改写 NBT 里的 `DataVersion`，让游戏当成当前版本的世界。
3. **进入世界**：1.20 起有 `--quickPlaySingleplayer`，启动后直接进测试世界。更早的版本没有这个参数，不能实测，仍用公式。
4. **自动飞行**：世界里放一个数据包（格式号取自 `version.json` 的 `pack_version`；1.21 起目录名从 `functions` 改成 `function`，两个都写）。玩家进来后切到旁观模式，每 tick 向前一格、高度 140，持续生成新区块；第 200 tick 和第 1400 tick 用 `say` 打出开始、结束标记。启动器从标准输出里读到标记就计时，结束后直接结束进程。

## 3. 测什么

每轮 JVM 加 `-Xlog:gc,gc+phases:file=nailong-gc.log:uptime`，从 GC 日志和进程 CPU 时间里取：

| 指标 | 来源 |
|---|---|
| 加载时间 | 启动到进入世界 |
| 服务端速度 | 1200 tick ÷ 计时段秒数，满速 20 |
| CPU | 计时段内进程 CPU 秒数 ÷ 墙钟秒数，等于平均占用几个核（Linux 读 `/proc`，Windows 用 `GetProcessTimes`） |
| 停顿 | 计时段内每次停顿的时长、P95、最长、超过一帧（16.7 ms）的次数 |
| 整堆回收、晋升失败 | 整轮的 `Pause Full`、`Evacuation Failure` / `To-space exhausted` |
| 存活数据 | 清理过老年代的回收（G1 混合/整堆、ZGC 大回收）之后的最大占用 |

**没有测帧率。** 原版没有把帧率写进日志的办法，要测得装一个配套 Mod。回收停顿是 JVM 参数真正能影响的部分，停顿超过一帧就是一次掉帧。

## 4. 三轮测试

1. **测量内存（G1）**：堆给公式需要量的 1.5 倍，再加 `-XX:-G1UseAdaptiveIHOP -XX:InitiatingHeapOccupancyPercent=20`，让 G1 频繁做并发标记和混合回收，回收后的占用就贴近真实存活数据。
2. **验证 G1**：正式参数，堆 = 存活 ÷ 0.6（G1 至少留 20% 新生代、20% 预留，存活最多占 60%），且至少比存活多 1 GB，向上取整到 512 MB，不超过电脑上限。出现整堆回收或晋升失败就加 1/4 再验证一次。
3. **对比 ZGC**：只在 Java 21+、64 位、不是 GraalVM 时跑。堆 = 存活 ÷ 0.5，且不少于 G1 的 1.25 倍；电脑放不下就跳过。

**选哪个：**

- 一般版本：G1 每分钟有 1 次以上超过一帧的停顿、或最长停顿 ≥ 30 ms，且 ZGC 最长停顿更短、服务端速度不低于 G1 的 97%、平均多用的 CPU 不超过总线程的 10%，才换 ZGC。否则 G1。
- 官方默认是 ZGC 的版本（26.1 起）：沿用 ZGC，除非它服务端速度低于 G1 的 95%，或多用的 CPU 超过总线程的 20%。

## 5. 结果怎么用

结果按「版本 + 游戏目录」存进 `<数据目录>/bench.json`，带一个指纹：Mod 文件名和大小、Java 大版本、电脑内存（整 GB）。指纹不变时：

- 内存为「自动」：堆用实测值（G1 或 ZGC 各自的），仍受电脑上限约束。
- 回收器为「自动」：用实测结论，优先于官方默认和公式。
- 手动内存、手动回收器、额外 JVM 参数照样优先。

## 6. 验证

单元测试覆盖版本信息解析、26.x 模板改写、两个时代的世界和数据包、选项文件、G1/ZGC 日志解析、堆计算和回收器决策。实机（Linux、16 线程、16 GB、Xvfb + llvmpipe 软件渲染）：

| 版本 | 存活数据 | 过程 | 结论 |
|---|---:|---|---|
| NeoForge 1.21.1（无 Mod） | 0.5 GB | G1 2 GB 无整堆回收，一次 17 ms 停顿；ZGC 无停顿、CPU 相同 | G1 · 2 GB |
| 26.3 原版 | 0.6 GB | G1 2 GB 有 3 次晋升失败，加到 2.5 GB 后每分钟 6 次超过一帧（最长 24 ms）；ZGC 无停顿、CPU 不多 | ZGC · 3.5 GB |
| 1.20.1 原版 | 1.0 GB | Java 17，不测 ZGC；G1 2 GB 无超过一帧的停顿 | G1 · 2 GB |

界面上从确认弹窗到进度页、跑完回到设置显示结论，完整走过一次。软件渲染下 CPU 多被渲染占用，真实显卡上的数字会不同；Windows 实机和大型整合包尚未实测。
